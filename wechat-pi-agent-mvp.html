微信 iLink × Pi SDK × Codex 订阅

一个本机运行、单微信用户、文本回复并支持图片理解的 Agent MVP。腾讯 iLink 负责微信收发；运行时以 Pi SDK 方式组合 pi-coding-agent、pi-agent-core 与 pi-ai，不拉起 CLI 子进程；首次启动直接通过 ModelRuntime.login() 完成 Codex OAuth 和模型绑定。

版本 v0.1 方案 部署：本机单用户 运行时：Node.js ≥ 22.19 存储：SQLite + Pi JSONL 受限工具：Skill 只读 · 沙箱写入 · 公网 HTTPS

1.1 最重要的技术选择：用 Pi SDK，不用 Pi CLI 承载运行时

pi-ai

Provider 层。统一模型类型、catalog、流式调用与各 Provider 协议；openai-codex 就在这一层。业务代码不直接拼 OpenAI 请求。

pi-agent-core

Agent 循环层。处理模型调用、消息、tool call 和多轮循环；它位于 pi-ai 之上。

pi-coding-agent SDK

Harness / Session 层。提供 createAgentSession()、SessionManager、ModelRuntime 和事件；这是包内 SDK，不等于启动 pi 命令。

结论：你的理解是对的：各种模型 Provider 的统一接入核心在 @earendil-works/pi-ai。本服务在进程内使用 Pi SDK；不通过 stdin/stdout 驱动 CLI，也不把 CLI 当常驻或首次登录入口。首次启动由 ModelRuntime.login(provider, "oauth", interaction) 打开浏览器完成 OAuth，再通过 Provider catalog 获取可用模型并保存用户选择；会话运行仍由 pi-coding-agent SDK 组合 pi-agent-core + pi-ai。

1.2 组件职责与所有权

组件拥有的数据 / 规则明确不负责
iLink Adapter协议 DTO、header、cursor、context token、重试分类不决定 Turn 状态，不感知 Pi 类型
Application Use Cases处理顺序、事务边界、FIFO、恢复、端口调用不直接发 HTTP，不解析 Provider 响应
DomainSession / Turn / Step / Outbox 实体、状态迁移与不变量不 import Pi、SQLite、Pino、HTTP SDK
PiAgentGateway业务 Turn 与 Pi AgentSession 的映射、事件翻译、最终文本不拥有业务去重、outbox 或 iLink token
SQLite Repositories业务状态持久化、唯一约束、claim / lease不解析或修改 Pi JSONL
Pi SessionManagerPi 原生消息树、compaction、model/tool messages不作为业务 Turn 状态的唯一事实源

2. 关键决策摘要

方案优先验证“微信消息能可靠地进入 Pi、由 Codex 订阅模型处理、再可靠回复微信”，并从第一天保留可定位问题的执行链路。

1
单进程模块化单体

避免早期微服务复杂度，同时保持边界可拆分。

FIFO
每个会话串行执行

避免同一 Pi Session 并发写入和上下文竞态。

2 层
SQLite + Pi JSONL

业务执行索引与 Agent 原生会话分别持久化。

E2E
全链路关联 ID

从 iLink message_id 一路追到 Pi step 和回复 client_id。

推荐结论：Provider 接入使用 pi-ai，Agent loop 使用 pi-agent-core，会话与 harness 使用 pi-coding-agent SDK。首次启动也不依赖 Pi CLI：应用直接调用 SDK OAuth、发现 Provider 可用模型并保存绑定；后续由同一 SDK 读取和刷新受保护的 auth.json。
两个强制 Spike Gate：编码前先验证 ① 当前账号可脱离 OpenClaw 通过 iLink HTTP 完成扫码、收取和回复一条文本；② 当前 Pi + ChatGPT Plus/Pro OAuth 可以在目标机器完成登录、刷新并执行一次无工具 Turn，且这种个人本地桥接符合当前服务政策。任一不成立就停止后续实现。
1
微信层：基于官方 openclaw-weixin 源码中公开的 iLink HTTP/JSON 协议，自建最小 TypeScript Client；MVP 提供二维码登录、文本收发、图片下载解密与理解、typing 和长轮询。
2
Agent 层：使用 @earendil-works/pi-coding-agent 的 createAgentSession()、ModelRuntime、SessionManager 和事件订阅。
3
控制层：应用自定义 Session → Turn → Step 模型，SQLite 记录状态机、去重、游标、outbox、错误与耗时；Pi JSONL 保留完整 Agent 对话树。
4
运维层：Pino JSON 日志、Prometheus 指标、Pi Telemetry → OpenTelemetry 适配、仅监听 localhost 的健康检查和 Turn 查询接口。

3. 目标与边界

必须完成（MVP）

  • 微信扫码绑定，安全保存 iLink bot token。
  • 用实测确认的不可变 sender ID 做精确 allowlist，未知发送者在模型调用前丢弃。
  • 长轮询接收文本和图片消息；图片经微信 CDN 下载、AES 解密后持久化，游标落盘并支持重启恢复。
  • 同一用户消息串行交给 Pi Agent Session。
  • 通过 Pi 的 openai-codex provider 使用 ChatGPT Plus/Pro OAuth。
  • 汇总 Pi 流式输出后，以文本回复微信。
  • 完整记录 session / turn / step 状态、错误、耗时和关联 ID。
  • 提供 /healthz、/readyz、/metrics 和本地诊断查询。

暂不完成（非目标）

  • 微信群聊、多租户、多微信账号、公网 SaaS。
  • 语音转写、视频理解和通用文件解析；图片 CDN 下载解密已纳入当前实现。
  • 边生成边向微信流式刷屏；MVP 只发送最终答案。
  • 生产级 OS/容器 Shell 隔离；当前本机 Bash 仅在显式高风险开关下启用。
  • 分布式调度、Kafka、Redis、Kubernetes。
  • 严格 exactly-once；MVP 采用 inbox/outbox + 幂等键实现可控的 at-least-once。
产品边界：iLink ClawBot 是“用户与自己的 AI 服务之间的私聊通道”，不是读取个人微信全部聊天的 API，也不是操作微信联系人、朋友圈或群聊的自动化接口。

4. 核心时序

① iLink Poller 收到更新
解析 message_id、seq、from_user_id、context_token 和文本。
② 原子写入 inbox + 新 cursor
同一个 SQLite 事务内插入消息并更新 get_updates_buf；唯一键阻止重投创建重复 Turn。
③ 创建或找到业务 Session
Session key = weixin:{bot_id}:{peer_id}。默认长期复用，用户发送 /new 时归档并新建。
④ 创建 Turn 并入 FIFO
一条入站用户消息对应一个业务 Turn。若 Agent 正忙，新消息保持 QUEUED，不使用 Pi steering。
⑤ 恢复或创建 Pi AgentSession
用数据库中的 pi_session_file 打开原生 JSONL；无映射时由 SessionManager.create() 新建并回写。
⑥ 执行 session.prompt()
订阅 Pi 事件，聚合文本 delta；将 agent、Pi turn、LLM、tool 事件写成 Step 和 Trace。
⑦ 生成 outbox
最终文本先持久化，再创建带稳定 client_id / run_id 的出站记录。
⑧ 调用 iLink sendMessage
携带目标用户和当前 context_token；成功后 Turn → SUCCEEDED，失败则按退避策略重试。

5. Pi SDK、Provider 与 Codex 订阅

已确认能力：@earendil-works/pi-ai 是统一 LLM API / Provider 层，内建 openai-codex，支持 ChatGPT Plus/Pro OAuth；pi-agent-core 在它之上实现 Agent loop；pi-coding-agent 同时提供 CLI 和可嵌入 SDK。运行时选择 SDK，并不意味着必须使用 CLI。

5.1 三层依赖关系

包职责本方案如何使用
@earendil-works/pi-ai统一 Model / Provider 类型、模型目录、stream / complete、OAuth provider 能力Provider 接入的事实边界；选择 openai-codex 模型
@earendil-works/pi-agent-core消息状态、Agent loop、tool call 循环和事件由 coding-agent SDK 组合；业务层不直接依赖其事件类型
@earendil-works/pi-coding-agentAgentSession、SessionManager、ModelRuntime、compaction、SDK 与 CLI UI只 import SDK exports；绝不 spawn pi 进程
为什么不只依赖 pi-ai？pi-ai 已经解决“怎么调用不同模型 Provider”，但不负责本方案需要的完整 coding-agent 会话 JSONL、compaction、工具事件与 AgentSession 生命周期。如果产品最终只是单轮聊天且应用愿意自行管理消息历史，可以改为直接组合 pi-agent-core + pi-ai；当前 MVP 复用 coding-agent SDK 更省实现成本。

5.3 OAuth 与模型绑定：应用内首次启动向导

const runtime = await ModelRuntime.create({ authPath, modelsStorePath });

if (!(await runtime.checkAuth("openai-codex"))) {
  // notify(auth_url) 时打开系统浏览器；prompt() 处理登录方式或验证码。
  await runtime.login("openai-codex", "oauth", interaction);
}

const models = await runtime.getAvailable("openai-codex");
const selectedModelId = await promptUserToSelect(models);
await saveNonSecretSettings({ provider: "openai-codex", selectedModelId });

首次启动统一检测：缺 iLink 凭证则扫码，缺 Codex OAuth 则由 pi-ai Provider 流程打开浏览器，缺模型绑定则展示当前账号可用 catalog。OAuth 凭证写入 ~/.pi/agent/auth.json，模型选择写入本地非敏感 settings；应用不复制 access token、不自行拼 OAuth 请求，也不要求用户先进入 Pi CLI。

5.4 SDK 集成骨架

import {
  createAgentSession,
  ModelRuntime,
  SessionManager,
} from "@earendil-works/pi-coding-agent";

const modelRuntime = await ModelRuntime.create({
  authPath: process.env.PI_AUTH_PATH,
  modelsStorePath: process.env.PI_MODELS_STORE_PATH,
});

// ModelRuntime 组合了 pi-ai 的 catalog / provider 与凭证解析。
const model = modelRuntime.getModel(
  "openai-codex",
  process.env.PI_MODEL_ID ?? "gpt-5.5",
);
if (!model) throw new Error("Configured Codex model is unavailable");

const { session } = await createAgentSession({
  cwd: WORKSPACE_ROOT,
  model,
  thinkingLevel: process.env.PI_THINKING_LEVEL ?? "medium",
  modelRuntime,
  sessionManager: SessionManager.open(piSessionFile),
  resourceLoader, // 独立 System Prompt + 本地 Pi Skills
  customTools: [safeRead, listFiles, sandboxWrite, publicHttpsGet],
  tools: ["read", "list_files", "sandbox_write", "http_get"],
});

// PiAgentGateway 内部调用；Application 层只看 Agent。
await session.prompt(userText);
模型 ID 不写死到业务逻辑：Provider 固定为配置项 PI_PROVIDER=openai-codex，模型用 PI_MODEL_ID，thinking 用 PI_THINKING_LEVEL。启动时由 adapter 验证 provider、模型和 OAuth；业务 use case 不认识这些配置细节。示例模型名仅为占位，必须以目标账号当时可见 catalog 为准。

5.5 Pi 事件如何进入 Step

agent_start / agent_end根 Step：agent_runagent_end 可能伴随后续 retry；仅在 agent_settled（若当前版本提供）或 awaited prompt() 与订阅者全部完成后结算业务 Turn。

6. 微信 iLink 接入

6.1 MVP Client 能力

认证

get_bot_qrcode → get_qrcode_status，取得 bot_token、bot id、user id 和服务端返回的 base URL。

接收

getupdates 长轮询，使用并持久化 get_updates_buf，支持 AbortSignal、超时、重试和退避。

发送

sendmessage 发送文本；使用稳定 client_id、run_id、目标 user id 和对应 context_token。

6.2 内部接口

interface ILinkClient {
  startQrLogin(): Promise<QrLogin>;
  waitForQrLogin(login: QrLogin, signal: AbortSignal): Promise<ILinkCredential>;
  getUpdates(cursor: string, signal: AbortSignal): Promise<UpdateBatch>;
  sendText(message: OutboundEnvelope, signal: AbortSignal): Promise<SendResult>;
  getConfig(userId: string, contextToken?: string): Promise<ILinkConfig>;
  sendTyping(userId: string, ticket: string, active: boolean): Promise<void>;
}

6.3 协议约束

  • 认证头包含 AuthorizationType: ilink_bot_token 和 Authorization: Bearer ...。
  • 遵循官方 Client 的 iLink-App-Id、client version、随机 X-WECHAT-UIN 和 base_info.bot_agent 约定。
  • 扫码后可能返回新的 baseurl 或重定向 host；后续请求必须使用有效地址，而不是永远写死初始域名。
  • get_updates_buf 是 opaque cursor，成功的空消息批次也可能推进；只有协议级成功（不只是 HTTP 200）时才与该批 inbox 原子提交。
  • context_token 属于短期会话材料：不得打印到日志；出站必须绑定“触发当前 Turn 的入站记录”里的 token，而不是会话最新 token，以免并发消息串线。
  • 必须先在真实 payload 中验证 sender ID 的不可变性，再把它作为 allowlist 主键；显示名不能用于鉴权。
  • MVP 文本长度按 3,500 字符安全分片，低于官方插件的 4,000 字符 channel limit。
稳定性声明：iLink 目前是 ClawBot 配套通道协议，而不是承诺长期稳定、面向任意第三方的通用微信 OpenAPI。实现应隔离在 adapter 内，pin 参考源码 commit，并准备协议兼容测试。

7. Session / Turn / Step 管理

避免“Pi turn”和“用户的一轮对话”语义冲突：本方案的 Turn 是一条微信入站消息驱动的完整业务执行；Pi 的 turn_start/end 被映射为 Turn 下的 pi_llm_round Step。

Session

一段连续的用户对话和 Pi 原生会话映射。

  • 键：channel + bot + peer
  • 默认长期 ACTIVE
  • /new 后归档
  • 关联 Pi session file

Turn

一条用户消息从收到到最终回复的业务事务。

  • 唯一绑定 inbox message
  • 同 Session FIFO
  • 拥有 trace_id / run_id
  • 保存最终答复和 usage

Step

Turn 内一个可计时、可失败、可追踪的原子活动。

  • LLM round
  • tool call
  • compaction / retry
  • outbound delivery

7.1 状态机

对象主路径异常终态恢复策略
SessionACTIVE → ARCHIVEDCORRUPTEDPi JSONL 无法打开时冻结旧 Session，新建 Session，并保留诊断记录。
TurnRECEIVED → QUEUED → RUNNING → REPLY_PENDING → SUCCEEDEDFAILED / DEAD_LETTER / CANCELLED依据是否已有 final_response 决定只重发还是人工/命令重试 Agent。
StepPENDING → RUNNING → SUCCEEDEDFAILED / SKIPPED / INTERRUPTED进程启动时将残留 RUNNING 标记为 INTERRUPTED，禁止假装成功。
OutboxPENDING → SENDING → SENTRETRY_WAIT / DEAD_LETTER稳定 client_id + 指数退避；是否被服务端幂等需实测。

7.2 并发规则

  • 同一 Session：并发度固定为 1；同一时刻只有一个 Turn 可以是 RUNNING/REPLY_PENDING。
  • 全局 MVP：单用户，因此全局 worker 并发度也设为 1，减少 OAuth、JSONL 和工具竞态。
  • 流式期间新消息：落 inbox 并排队，不调用 steer()；未来可按命令显式增加 /steer。
  • 命令优先级：/status、/cancel、/new 在 router 层处理，不进入普通 Agent prompt。

8. 持久化设计

8.1 数据所有权

SQLite：执行控制面

负责 inbox/outbox、游标、Session 映射、Turn/Step 状态、错误、耗时、重试、final response 和诊断索引，是崩溃恢复的依据。

Pi JSONL：Agent 上下文面

由 Pi SessionManager 管理完整消息树、模型信息、工具消息、compaction 和分支。应用不自行重建 Pi 的内部格式。

8.2 最小表设计

表关键字段约束与用途
channel_accountsid, bot_id, user_id, base_url, credential_ref, status不存明文 token；credential_ref 指向受保护文件或 Keychain。
channel_cursorsaccount_id, cursor, updated_at每账号唯一；与 inbox 插入同事务更新。
inbox_messagesid, account_id, channel_message_id, seq, peer_id, context_token_enc, body_hash, raw_ref, statusUNIQUE(account_id, channel_message_id)；若 message_id 缺失，使用稳定 fingerprint。
sessionsid, channel, account_id, peer_id, pi_session_id, pi_session_file, status, last_turn_at同一 channel/account/peer 仅一个 ACTIVE Session。
turnsid, session_id, inbox_id, trace_id, run_id, status, queued_at, started_at, completed_at, final_response, error_codeUNIQUE(inbox_id)，一条入站消息只创建一个业务 Turn。
stepsid, turn_id, parent_step_id, ordinal, kind, name, status, started_at, ended_at, input_summary, output_summary, error_jsonUNIQUE(turn_id, ordinal)；记录执行树，不记录逐 token delta。

8.3 推荐 SQLite 配置

PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

单机 MVP 可使用 Node 内置 node:sqlite 或成熟 SQLite driver。所有事务保持短小，绝不跨越 HTTP、LLM 或 tool 执行；worker claim 使用条件更新/CAS（可配 owner、boot_id、lease_until）。若选择 Pi 的 SQLite session backend，也不要把它与应用 control-plane schema 混为一套所有权；Pi 存储视为 opaque，仅保存 pi_session_id 和 locator。

10. 安全边界

关键事实：Pi 官方说明其本身不提供文件系统、进程、网络或凭证访问的内建权限系统，默认拥有启动它的 OS 用户权限。因此“只在本机运行”不能代替 sandbox 和 tool policy。

MVP 默认策略

  • 使用独立 OS 用户运行服务。
  • 固定 WORKSPACE_ROOT，所有文件路径 realpath 后必须位于根目录。
  • 工具采用显式 allowlist：Skill/沙箱只读、沙箱写入与公网 HTTPS GET。高风险本机 Bash 由 TOOL_SHELL_ENABLED 单独控制，启用后继承 OS 用户权限且不受路径 jail 约束。
  • beforeToolCall fail-closed：未知工具一律阻断；bash、write、edit、delete、browser、网络请求和凭证读取始终关闭。
  • 同一时间只执行一个 Turn。
  • 管理 HTTP 只绑定 127.0.0.1。

凭证策略

  • Pi OAuth：沿用 ~/.pi/agent/auth.json，权限 0600。
  • iLink token：OS Keychain 优先；MVP 可用 0600 文件并在 SQLite 只存引用。
  • context_token：如需落库，用本机 master key 加密；日志全部 redact。
  • 启动时检查凭证文件 owner 和权限，不符合则拒绝 ready。
  • 诊断导出前二次脱敏，禁止打包 auth 文件。

后续写操作方案

Phase 2 再增加微信内审批：Agent 产生有副作用的 tool call → Step 进入 WAITING_APPROVAL → 微信发送参数摘要和一次性短码 → 用户回复 /approve CODE → 工具在 sandbox 中执行。审批必须绑定 turn、tool_call_id、参数 hash 和过期时间，不能只凭“确认”二字。

11. 幂等、重试与故障恢复

接收端：先持久化，再处理

getUpdates 返回后，在单个事务中完成 inbox 去重插入和 cursor 更新。即使服务随后崩溃，消息仍在本地队列；若服务端重投，唯一键将其识别为重复。

执行端：不盲目重跑有副作用 Turn

进程重启发现 RUNNING Turn 时，将未结束 Step 标记为 INTERRUPTED。如果 final_response 已存在，只恢复 outbox；否则 MVP 标记为 FAILED，允许用户发送 /retry <turnId>。默认无工具使人工重试风险可控；开启任何有副作用工具后必须改为 NEEDS_REVIEW，不得盲目重跑。

发送端：Outbox Pattern

回复文本与稳定 client_id 先落库再调用 iLink。网络超时无法确认是否已送达时复用同一 client_id 重试，但服务端是否对 client_id 提供强幂等需要集成测试验证；在确认之前对外只承诺“尽量避免重复”，不承诺 exactly-once。

退避策略

iLink poll：2s、5s、15s、30s 封顶并加 jitter；send：1s、3s、10s、30s，最多 5 次后 DEAD_LETTER；Codex provider retry 优先交由 Pi，自身只记录 Pi retry event，不做双层无限重试。

单实例、Lease 与恢复所有权

主防线使用 OS singleton lock，避免两个进程同时 long-poll；SQLite claim 额外记录 owner、boot_id、lease_until。启动时可立即回收同一旧 boot 的 claim，其他 owner 仅在 lease 过期后回收。绝不在数据库事务内等待网络或模型。

优雅停机

收到 SIGTERM 后：停止发起新 poll → abort 当前长轮询 → 停止取新 Turn → 等待当前 Pi Turn 在限定时间内结束 → flush DB/log/trace → 退出。超时则把运行中 Step 标记为 INTERRUPTED。

12. 预期文件结构与领域分层

采用轻量 Hexagonal Architecture：Domain → Application → Interfaces ← Adapters。目录按依赖规则而不是第三方库名字组织，Pi 与 iLink 都只能出现在 adapter / infrastructure 层。

12.1 领域划分

Messaging

入站/出站消息、channel message ID、sender identity、文本与命令。只表达通道无关语义。

Conversation

业务 Session、SessionKey、上下文延续与归档；只保存 Pi session locator，不理解 JSONL 格式。

Execution

Turn、Step、状态机、FIFO 与错误分类，是整个应用的核心领域。

Delivery

Outbox、chunk、delivery attempt、幂等键和不确定发送结果。

Policy 是横切领域规则：SenderPolicy 决定谁能触发模型；ToolPolicy 决定 Agent 能调用什么。两者的规则接口放 Domain，读取配置和挂接 Pi hook 的实现放 Adapter。

13. 实施计划

P0 · 兼容性 Spike Gate（1–2 天）

P1 · iLink 文本通道（1 天）
QR、token store、getUpdates、sendMessage、mock server、协议 fixture；先用 echo handler 跑通。
P2 · Pi Agent 集成（1 天）
ModelRuntime、AgentSession、默认无工具的 fail-closed policy、最终文本聚合、错误分类。
P3 · Session / Turn / Step（1 天）
状态机、Pi JSONL 映射、FIFO、inbox/outbox、命令路由。
P4 · 可观测性与恢复（1 天）
Pino、metrics、trace adapter、debug API、重启恢复和 fault injection。
P5 · 硬化和验收（0.5–1 天）
脱敏测试、权限检查、长消息分片、OAuth 过期、iLink 网络错误、文档和一键启动。

14. MVP 验收标准

功能

  1. 首次启动可展示二维码并完成 iLink 登录。
  2. 微信发送文本后，Pi 使用 openai-codex 生成回答并回复。
  3. 连续发送 3 条消息时按顺序回复，不并发污染上下文。
  4. /new 创建新 Pi Session；/status 返回脱敏状态。
  5. 超过单条限制的回复可安全分片。

可靠性与诊断

  1. 在消息入库后 kill 进程，重启后仍能处理该消息。
  2. 同一 iLink message 重投不会创建第二个 Turn。
  3. send 超时会进入 outbox retry，并可看到 attempt。
  4. 任一失败可用 turn_id 查到完整 Step 树和根因分类。
  5. 日志扫描测试证明 token、Authorization 和 context_token 未泄漏。

建议的演示脚本

1. 启动服务，展示 /readyz 因“iLink 未登录”返回 not-ready
2. 扫码后 ready
3. 微信发送：“用三点说明这个 Agent MVP 的主要风险”
4. 展示 typing → 最终回复
5. 用 turn_id 打开 /debug/turns/:id，展示 llm_round / send Step（可选只读工具 profile 再展示 tool_call）
6. 发送第二条追问，证明 Session 上下文延续
7. 重启进程，再次追问，证明 Pi JSONL 与 SQLite 映射恢复
8. 展示 /metrics 和脱敏 JSON log

15. 风险与待确认项

风险影响MVP 应对
iLink 协议并非稳定公共 OpenAPI字段、header、登录或路由发生变化隔离 adapter、pin 官方参考 commit、contract fixture、启动自检。
账号未获得 ClawBot/iLink 能力二维码或授权流程无法完成P0 首先验证，不进入后续开发。
Codex 订阅 OAuth 条件变化登录失败、模型不可用，或无人值守桥接不符合当前政策/额度P0 核对当前 OpenAI/Pi 文档与账号政策；readiness 检查；模型配置化；不承诺 API key 自动兜底。
sender ID 语义未验证allowlist 可能绑定到不稳定标识，造成越权或误拒绝真实 payload Spike；只用实测不可变 ID，显示名绝不鉴权。
Pi API/包名继续演进SDK 代码失效精确 pin @earendil-works/pi-* 版本并锁定 Node 版本。
工具越权微信 prompt 导致本机文件、内网或命令风险显式工具白名单；Skill/文件路径 jail；写入独立沙箱；公网 HTTPS 校验。本机 Bash 默认关闭；若显式开启，必须接受其拥有完整 OS 用户权限的风险。
SQLite 与 Pi JSONL 双持久化不一致Turn 找不到对应 Pi 上下文SQLite 保存文件引用；打开失败则归档旧 Session，不伪造恢复。
发送结果不确定网络超时后重复回复稳定 client_id + outbox；实测服务端幂等，文档不承诺 exactly-once。
进入编码前必须关闭的 Gate：当前微信账号能够直连完成 ClawBot/iLink 扫码、收发和 sender ID 鉴权验证；应用内 ModelRuntime.login() → ChatGPT Plus/Pro (Codex) 在目标机器上成功，Provider catalog 能返回可用模型，并确认个人本地无人值守桥接符合当前账号政策与额度。不要只凭“登录成功”推断长期支持。
