# 截图与微信图片回复

适用：F-002、migration 10、本地实现验证日期 2026-09-10。真实微信发送、实际宿主桌面采集仍须现场验收。[规格](../specs/image-delivery/spec.md) · [验证记录](../specs/image-delivery/evidence/README.md)

## 使用与验收

1. 更新依赖并使用通过完整检查的构建；计划重启前备份 app.db 及对应 WAL 数据，勿用旧二进制打开 migration 10 数据库。
2. 图片回复默认接入，无需新增环境变量。截图 Skill 沿用原有 Pi Skill 加载配置。按正常停止/启动流程重启；启动会依项目既有策略结束旧会话，不在有重要运行任务时直接杀进程。
3. 先用自己指定的非敏感 PNG/JPEG，请助手“把这张图片发给我”；确认 reply_image 登记成功、Task Review 通过、Outbox SENT，并在微信中打开图片。
4. 再验证公开测试网页截图；最后在用户明确请求的范围验证桌面截图。不要将私人桌面自动上传作为默认探针。

图片回复不设单独开关；实际读文件和截图仍遵循用户权限。本次代码交付不自动修改本机 .env 或重启服务。

## 可用方式

图片由现有 Skill、脚本或 bash 生成，保存到个人工作目录，例如 output/screenshot.png，然后调用 `reply_image({path:"output/screenshot.png"})`。工具不直接发微信，而是保存快照、登记当前 Task 版本的候选附件；审核通过后发送。最多 3 张，需替换时先 `reply_image({action:"clear"})`。

PNG/JPEG 上限 10 MiB、2500 万像素，单用户快照额度 500 MiB。不支持格式或超限明确报错，不自动降质。用户只要图片时，已验证附件允许空文字完成申请；无附件的空回复仍拒绝。

## 网页截图失败

已验证的故障机制：长工作目录被用作 TMPDIR，Playwright socket 路径过长；关闭全部浏览器不能修复路径长度。当前执行器使用每次独立的短临时目录，并在 sandbox wrapper 内显式传递，避免运行时覆盖。

优先使用项目 [screenshot-reply Skill](../../skills/screenshot-reply/SKILL.md)。打开、截图、关闭放在同一次 bash 调用，使用唯一会话和 trap；不执行 kill-all。截图文件不能保存在 TMPDIR，命令结束时该目录会被清理。旧全局 Skill 配套引用缺失时不要反复读取不存在文件，项目 Skill 提供完整单文件流程。

本地实测已经通过项目执行器打开 about:blank、截图并关闭，生成有效 PNG。它不证明飞书文档已登录、互联网网页可达或微信已收到图片。独立会话不继承个人浏览器登录态；登录页不冒充目标文档。

## 桌面截图失败

`could not create image from display` 只证明采集失败。检查当前微信助手由哪个程序启动、该程序的 macOS 屏幕录制授权，以及是否有可访问的图形会话；必须从相同服务启动链重试。Full Access 只是应用内当前账号的执行权限，不能替代系统采集授权。

不通过自动提权、修改系统权限数据库或重启用户桌面绕过该问题。当前没有新增原生桌面 helper，也未验证实际宿主的桌面采集成功。

## 生成成功但没收到

在 Task Trace 分清：图片登记 → Review → 上传 → 发送。登记回执不是送达，上传成功也不是送达。文字和图片独立 Outbox 项，前项重试会阻塞同回复后续图片。

- 审核未通过、任务取消或版本过期：候选图片不进入 Outbox。
- 上传失败：队列重试，不重新运行 Agent 或截图。
- 已上传但发送失败：复用已保存引用；凭据更换后重新上传。协议未给出可靠引用有效期，不能根据时间猜测失效。
- 发送超时：远端可能已经收到；稳定 client_id 不等于已证实的远端恰好一次。
- DEAD_LETTER：保留失败记录和原图，其余片段保持阻塞。先查阶段与认证/通道问题，确认微信实际是否收到，再明确选择是否创建新的发送请求；不要直接批量重置全部 Outbox 或删除数据库。

图片引用、AES key 和签名信息仅保存在权限收紧的应用数据库中，不出现在普通 Trace。排障不要把数据库或原始图片整体上传到报告。

## 存储清理

启动前台工作循环之前清理：孤儿快照至少 24 小时，终态且无待投递引用的快照至少 7 天。清理保留元信息，非终态任务、重试、死信和阻塞消息的原件不会自动删除。

长期运行或死信累积可能触发配额；维护重启仅回收满足条件的文件，不解除死信引用。需要丢弃失败投递时应先停止服务、备份并针对明确任务制定处置，不提供不加选择的删除命令。运行配置的其他变化不会自动清空图片文件。

## Review 反复要求核验图片

Review 是无工具的交付检查，普通截图/发图以可信登记附件和连贯执行结果为依据。缺少像素视图不等于图片错误，不应要求再次打开网页、OCR 或重复截图；历史 Review 意见也不自动成为新验收要求。

需要返工的情况是可观察的实际缺口，例如附件没有登记、截图命令失败、已知停在登录页而用户要求正文，或用户明确要求视觉核验但尚未执行。返工动作只补这个缺口。权限和 Task 版本门槛保持原样。

合成场景评估可显式运行 `./node_modules/.bin/tsx scripts/evaluate-task-review.ts <结果文件>`，会使用本机已认证模型产生真实调用费用/额度消耗，只发送合成文本场景，不操作浏览器或给微信发消息。当前样本结果见 [Review 评估](../specs/image-delivery/evidence/review-evaluation.json)，不视为所有未来回答的确定性保证。
